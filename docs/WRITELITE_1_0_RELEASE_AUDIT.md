# WriteLite 1.0 — аудит релиза

Документ фиксирует, что именно было проверено и изменено при подготовке
публичного релиза WriteLite 1.0.0, и на каком основании. Каждое утверждение
здесь опирается на воспроизведённый прогон, а не на чтение кода, если не сказано
обратное.

## 2. Найденные и исправленные проблемы

### 2.1. Восемь падающих тестов на самой базе

На `110a676a` тестовый набор **не был зелёным**: 8 из 1549 тестов падали. Все
восемь — следствие переезда строк интерфейса в `Resources/Strings.resx`. Сборка
проверяет только *имена* ключей (генератор создаёт по свойству на запись resx),
значения не проверял никто.

**Карточка исправления**

| Что видел пользователь | Причина | Исправление |
|---|---|---|
| Кнопка основного действия при вставке знака читалась «запятую», «точку» | значения `Corr_Add*` потеряли глагол | возвращено «Добавить запятую» и т. д. |
| Слова нет в словаре, а карточка писала «Слово не найдено в тексте» | `Corr_WordNotFound` | «Слово не найдено в словаре» |
| Пояснение карточки — обрывок «…для «{0}».» | `Corr_NoConfidentFixForWord` | «WriteLite не удалось подобрать уверенное исправление для «{0}».» |
| Кнопка восстановления читалась «Копировать» | ссылалась на `Strings.EditorAi_Copy` — ключ панели ИИ в редакторе | добавлен собственный ключ `Corr_Copy` = «Скопировать» |

### 2.2. Страница диагностики не показывала данные

Пятнадцать строк-шаблонов на странице «Диагностика» потеряли `{0}`.
`string.Format` молча отбрасывает лишний аргумент, поэтому блоки «Активное поле»,
«Движок» и «Система» выводили голые подписи: «Поле», «Процесс», «Статус» — без
единого значения. Это ровно та страница, которую просят прислать при обращении в
поддержку.

Найдено не по падающему тесту, а сверкой арности: для каждого вызова
`string.Format(Strings.X, …)` сопоставлено число аргументов с числом
подстановок в resx. Исправлено во всех 15 ключах; инвариант закреплён тестом
`StringResourceIntegrityTests`.

Подтверждено визуально на установленной сборке: `Поле: Нет`, `Замечаний: 0`,
`Статус: Языковой движок готов`, `Версия: 1.0.0.0`.

### 2.3. Языковой движок не запускался вне машины разработчика

**Самая серьёзная находка релиза.**

`ThirdParty/LanguageEngine/6.4` — это LanguageTool 6.4, то есть Java. В
репозитории нет JVM, и в установщике 1.0.0 её тоже не было: проверено по
`install.log` прошлой сборки — среди 2333 установленных файлов ни одного
`java`/`jre`.

`WriteLiteJavaResolver.EnumerateCandidates` ищет по порядку: заданный путь,
**`{BaseDirectory}\Runtime\Java\bin\javaw.exe`**, `JAVA_HOME`, `PATH`. Второй
пункт — зарезервированное место для поставляемой среды, и оно пустовало. На
машине без системной Java хост бросал `java-not-found`, переходил в
`Unavailable`, и продукт молча опускался до собственной базовой проверки. На
машине разработчика с JDK в `PATH` это не воспроизводится — поэтому и ушло в
релиз.

Исправлено в `build/build-release.ps1`: собирается образ `jlink` (~50 МБ) и
кладётся в `Runtime\Java`. Модули:
`java.se,jdk.httpserver,jdk.unsupported,jdk.crypto.ec,jdk.localedata,jdk.zipfs`.
`jdk.httpserver` **не входит** в `java.se`, без него сервер падает с
`NoClassDefFoundError: com/sun/net/httpserver/HttpHandler` — это проверено.

Сборка отказывается продолжать, если LanguageTool не ответил на
`/v2/languages` из собранной среды.

Проверено на установленной копии: процесс
`javaw.exe` из `Runtime\Java\bin`, в журнале
`language-engine-ready port=18081`.

### 2.4. Автозапуск из установщика не переживал первый запуск

Установщик пишет значение `HKCU\…\Run\WriteLite` до того, как появляется
`settings.json`. `App.OnStartup` затем приводил реестр в соответствие с
настройками, где `StartWithWindows` по умолчанию `false`, — и **удалял только что
записанное значение**. Галочка «Запускать WriteLite вместе с Windows» переставала
работать после первого же запуска.

Направление синхронизации теперь зависит от того, есть ли сохранённая настройка
(`AutostartReconciler`). Отдельно закрыт сценарий обновления: у пользователя уже
есть `settings.json` с выключенным автозапуском, он ставит галочку в
установщике — по одному только значению в `Run` «записано минуту назад» не
отличить от «устаревшая запись». Поэтому установщик оставляет одноразовую
пометку `HKCU\Software\WriteLite\Setup\AutostartRequested`, приложение читает её
один раз, переносит в настройки и удаляет.

Имена ключей в `WriteLiteSetupHandoff` и в `installer/WriteLite.iss`
сверяются тестом.

### 2.5. Идентичность продукта

В дереве не было ни `<Version>`, ни `<Product>`, ни `<Company>` — бинарники несли
умолчания SDK. Добавлен `Directory.Build.props` как единственное место, где
объявлена версия. Дополнительно отключён
`IncludeSourceRevisionInInformationalVersion`: SDK дописывал к
`InformationalVersion` хеш коммита, и `ProductVersion` уезжал в
`1.0.0+77c333f2…`.

Подпись в углу главного окна читалась «BETA · ЛОКАЛЬНО» — заменено на
«1.0 · ЛОКАЛЬНО».

### 2.6. Лишнее в установщике

Прошлый установщик нёс 221 файл сопроводительных ресурсов .NET для тринадцати
языков, которых в интерфейсе нет. Добавлено
`<SatelliteResourceLanguages>ru;en</SatelliteResourceLanguages>`.

### 2.7. Что проверено и признано не багом

Чтобы не выдавать наблюдения за дефекты:

* `ReadingPage._libraryStale` — поле присваивается и не читается. Выглядит как
  незавершённая функция, но `ShowLibrary()` вызывает `RenderLibrary()`
  безусловно, поэтому пользовательского эффекта нет.
* `HybridTextAnalysisService._cacheText/_cacheIssues/_cacheUtc` — остатки
  удалённого кеша, только обнуляются. Мёртвый код, не дефект.
* `WordChip.Language` скрывает `FrameworkElement.Language` (CS0108). Риск
  реальный, но воспроизвести отказ не удалось; переименование публичного
  свойства зависимости без доказанного отказа — рефакторинг ради рефакторинга.
* Массовое сокращение формулировок в resx (десятки строк) — редакторское
  решение автора рефакторинга, а не ошибка. Возвращены только те строки, где
  текст стал неверным по смыслу или оборванным.
* `catch { }` в `src/`: ровно один, `catch (ObjectDisposedException) { }` —
  конкретный тип, осознанный.
* TODO/FIXME/HACK в `src/`: ни одного. Путей разработчика в поставляемом коде
  нет (все вхождения `C:\Users\…` — фикстуры тестов).

### 2.8. Сайт выкладывал в деплой служебные файлы

Не дефект приложения, но нашлось при работе над публикацией и касается
приватности, поэтому записано здесь.

`vercel deploy` отправляет содержимое рабочего каталога, а не git-срез, и в
репозитории сайта не было `.vercelignore`. Список файлов предыдущего
production-деплоя (Vercel API, `list_deployment_files`) показывает, что вместе с
исходниками уехали:

* `.local-secrets/` — 7 файлов, включая `telegram-admin-claim.txt`,
  `vercel-preview.log`, `build.log` и `dev-server.pid`;
* `.tools/` — 13 файлов вендорных бинарников и архивов (97 МБ);
* `next.tgz`, `swc-15.5.7.tgz`, `eslint-config-next.tgz`.

Next.js наружу их не отдаёт — публично доступны только `public/` и результат
сборки, — так что публичной утечки не было. Но эти файлы лежали в хранилище
исходников деплоя и доступны всем, у кого есть доступ к проекту Vercel.

Добавлен `.vercelignore`, исключающий всё перечисленное. Шаблоны
`.env.example` и `.env.production.example` оставлены намеренно: в них только
имена переменных, без значений.

Существующие деплои этим изменением не очищаются — если содержимое
`.local-secrets/` считается чувствительным, старые деплои нужно удалить
отдельно, а `telegram-admin-claim` перевыпустить. Это решение владельца.

## 3. Сборка

```
dotnet restore WriteLite.sln
dotnet build   WriteLite.sln -c Release
dotnet test    tests/WriteLite.Tests/WriteLite.Tests.csproj -c Release --no-build
```

Публикация и установщик — одной командой:

```
pwsh build/build-release.ps1
```

Она прогоняет тесты, публикует self-contained `win-x64`, собирает среду Java,
**проверяет, что LanguageTool на ней поднимается**, чистит staging от `.pdb` и
журналов, компилирует Inno Setup и считает SHA-256.

Режим публикации — self-contained. Прошлый релиз был таким же (в его
`install.log` есть `coreclr.dll` и `hostfxr.dll`), и .NET 10 слишком новый, чтобы
между загрузкой и работающей программой стояла установка Desktop Runtime.

### 4.1. Репозиторий не может прогнать собственные тесты на чистом клоне

Обнаружено при настройке CI и подтверждено на раннере GitHub.

Сначала `dotnet restore` падал целиком:

```
error NU1301: The local source '…\ai\.nupkgs' doesn't exist.
```

`nuget.config` объявляет `ai\.nupkgs` источником пакетов, а `.gitignore`
исключал весь каталог. NuGet считает отсутствующий локальный источник ошибкой
всего восстановления, а не пропускает его, — то есть собрать проект из чистого
клона не мог никто, не только CI. Каталог теперь отслеживается через `.gitkeep`
(сами `.nupkg` по-прежнему игнорируются).

После этого сборка проходит, но тесты — нет: **79 из 1565**. Языковые данные,
против которых работают анализаторы (`resources/lexical/*.db`, частотные
таблицы, графы ONNX в `models/`), намеренно не в git — это многогигабайтные
артефакты, пересобираемые из `ai/scripts/`. Без них ранжирование кандидатов
даёт другой ответ: `привте` → `привое` вместо `привет`, `двер` → `двор` вместо
`дверь`.

Это не дефект продукта и не повод трогать тесты. Удалить их, пометить как
пропущенные или ослабить проверки ради зелёной галочки означало бы выбросить
единственный контроль над поведением языкового движка. Поэтому `ci.yml`
проверяет наличие данных и говорит прямо, что именно он прогнал:

* данные есть — полный набор;
* данных нет — сборка, проверка метаданных продукта и тот поднабор, который от
  корпуса не зависит (`StringResourceIntegrityTests`,
  `AutostartReconcilerTests`, `BundledJavaRuntimeContractTests`), плюс
  `::warning` в журнале.

Полный набор остаётся первым шагом `build/build-release.ps1`, который
отказывается собирать установщик из дерева с падающими тестами.

**Что это значит для проекта.** Публичный репозиторий в нынешнем виде не
самодостаточен: сторонний человек не соберёт установщик и не прогонит тесты.
Решение — хостинг данных с загрузкой по скрипту или Git LFS с отдельной квотой —
выходит за рамки этого выпуска и требует отдельного решения владельца.

## 6. Известные ограничения

* Установщик не подписан цифровым сертификатом — SmartScreen покажет
  предупреждение. Это указано на странице загрузки и на первом экране установки.
* CI не собирает установщик. Веса моделей (`models/*.gguf`, `models/*.onnx`) и
  лексическая база (`resources/lexical/*.db`) намеренно не в git — это
  многогигабайтные артефакты, пересобираемые из `ai/scripts/`. `release.yml`
  вместо этого проверяет, что тег зелёный и что выложенный файл совпадает с
  `SHA256SUMS.txt`.
* Проверка английского языка остаётся в разработке.
* Ускорение на GPU не поддерживается.
* При старте наблюдается разовая задержка диспетчера ~2 с
  (`ui-hang-suspected` → `ui-hang-recovered` в журнале); окно после этого
  отзывчиво.
